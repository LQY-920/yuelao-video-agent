# yuelao-video-agent 项目协作规则

版本：v1.0 · 2026-10-20。根据所有者已明确的会话分工与 GitHub 协作要求制定。

本规则用于同步到产品仓库的 `docs/project-governance.md`，并由仓库 `AGENTS.md` 和 `CONTRIBUTING.md` 引用。后续更新通过开发分支与 PR 同步；用户的新明确要求优先，旧规则与交接包同时修订，避免只在聊天里更改。

仓库：[LQY-920/yuelao-video-agent](https://github.com/LQY-920/yuelao-video-agent)，公开仓库。多个功能共同组成同一个网站。

## 1. 一个长期主会话，按功能建立次会话

- 主会话负责真实抖音运营、整体路线、功能优先级、模块间衔接、交接材料与实际使用验收。
- 每跑通一个可独立交付的操作，准备真实样例及验收条件，再新建对应功能会话，统一命名为 `yuelao-video-agent | 功能名称`。
- 现有 `yuelao-video-agent | 对标账号分析` 只负责对标账号分析模块及其运行所需的最小基础设施，不承担整站后续所有模块的开发。
- 后续例如 `yuelao-video-agent | 选题与排期`、`yuelao-video-agent | 脚本与分镜`，在对应操作跑通后分别创建。不预建空会话，不把每个小按钮拆成独立会话。
- 已有功能的修改回原功能会话。功能完成后进入维护状态；新功能进入新的对应会话。
- 前期通常只推进一个功能的开发。主会话继续运营，不以网站尚未完成为由停止真实内容制作。
- 用户已授权按上述条件创建和交接功能会话，无需每次重复询问。仅有规划、没有实际产物的环节继续留在路线图中。

## 2. 对标模块的当前边界

当前范围：账号链接与自身方向输入、材料整理与补充、带来源和覆盖范围的拆解报告、保存与导出、从报告中选取候选选题并保存/导出为交接卡。

候选选题卡应保留来源、适配理由、当时的账号背景及报告版本。它是后续选题模块的输入，不等于已排期或已进入制作。

完整选题池、最终入选决策、栏目配比、制作容量、发布日期、日历与排期管理属于未来“选题与排期”模块。脚本、分镜、生图、视频制作、发布及复盘也由对应会话承接。

当前允许建立对标模块所必需的页面框架、轻量背景输入、材料/报告/候选选题数据结构。共享能力的扩展应写清影响，交由主会话协调；不因路线图列出了后续模块就自行展开。

首轮交付为可点击的网站原型。真实保存、人工整理、历史样例和自动分析分别说明；抓取、模型或生图服务未接通时，不用预置结果冒充任意输入的真实分析。

## 3. 共用工程与开发分支

- 所有功能使用同一仓库，复用账号、材料、报告与内容任务等共享对象。各功能可以先实现所需的最小结构，后续兼容扩展。
- 一个主题一个开发分支。现有对标分支为 `feat/benchmark-analysis`；后续分支在交接时按功能确定，不为每个模块另建一套网站或重复仓库。
- 修改前读取工程 `AGENTS.md`、状态与相关踩坑记录，检查 `git status`，确认分支和工作树。
- 顺序任务可在前一任务完成、工作区干净且明确交接后复用检出目录。并行任务必须使用不同分支和工作树，不得并发修改同一检出目录。
- 新功能优先基于已合入的主线。需要尚未合入的依赖时，明确依赖 PR 和合并顺序，不隐式依赖另一个会话的未提交文件。
- 共享接口、组件和数据结构的修改，要在交接或 PR 中说明兼容影响；跨模块工作由主会话协调归属。
- 开发完成后运行与改动相称的检查，提交 PR，写明实现范围、验证结果、未接通能力和使用入口。原型完成、真实服务可用、运营验收和已合并分别记录。

## 4. 仓库权限与 main 规则

### 所有者

- 仓库所有者保留 Admin 权限，保留设置、成员邀请与权限管理能力。
- 可以创建 PR，自主合并自己的 PR，不依赖协作者批准。
- 日常仍遵循开发分支 → 测试 → PR → 所有者决定并执行合并的流程。管理员绕过权限用于保留控制权，不把它解释为日常直接修改 main 的流程。

### 协作者

- 新协作者授予 Write，不授予 Admin。
- 可以拉取代码、创建与推送开发分支、提交 PR、参与代码审查和 Issue 管理。
- 不得直接推送 main；即使 PR 已获批准，也不得自行合并到 main。最终由所有者审核并执行合并。

### main 分支保护

- 通过 PR 合入；要求至少 1 人批准。
- 关闭“对管理员强制执行”，保留所有者自主合并本人 PR 的能力。协作者仍受批准要求约束。
- 禁止强制推送，禁止删除 main。
- 另外启用分支规则集，精确匹配 `refs/heads/main`，启用 Restrict updates。
- 该限制更新规则集仅允许仓库管理员角色 Always bypass；普通 Write 协作者不得进入绕过名单。
- 不以“至少 1 人批准”替代限制更新规则；需分别核对两层配置。
- 禁止强推、禁止删除既是配置要求，也是项目行为规则；不要把管理员可绕过的配置描述为对管理员绝对不可绕过。
- 不自行降低保护强度，不把自主合并权限当作所有 PR 已获准合并。每次合并依据所有者的具体决定或已明确的任务授权。

## 5. 邀请和权限验证

- 当前暂不邀请协作者，不自动邀请任何用户名。
- 将来所有者明确要求邀请并提供 GitHub 用户名后，创建定向邀请，返回 GitHub 实际提供的接受链接。
- 邀请由对方登录被邀请账号后接受。“已发出邀请”和“已正式加入”分开记录。
- 核对所有者 Admin、协作者 Write、main 保护已开启、限制更新规则集 active、精确匹配 main、绕过名单仅含管理员角色。
- 配置回读通过与普通 Write 身份下的行为测试分开记录；没有协作者或没有执行测试时，不声称已实际测试越权推送/合并被拒绝。
- 规则变更或新增协作者后重新核对相关项。保留真实链接、检查结果和检查时间，不把网络失败记录为验证通过。

## 6. 交接与完成标准

主会话在创建功能会话前准备：任务目标、真实输入、最终运营产物、人工修改、缺失/失败情况、本次范围与排除项、验收用例、共享数据/接口依赖以及仓库信息。

功能会话交付：分支及工作树位置、实现范围、可运行入口、真实测试结果、待接通能力、PR 链接与需要衔接的模块。

主会话维护功能会话登记表，记录名称、会话 ID、功能、分支/工作树、PR、实现状态和运营验收状态。没有创建或交付的项留空/待定，不编造链接。

功能初验后，主会话在下一次真实操作中使用它，把问题交回原功能会话。合入后同步产品进度、交接记录和所用版本。

## 7. 运营材料与公开仓库

- 运营工作区与产品仓库分别管理。公共仓库只接收开发所需且已明确可公开的规则、代码与样例。
- 不将完整聊天记录、浏览器登录状态、凭据、客户材料或全部运营目录自动同步到公开仓库。
- 个人视觉素材及运营案例按具体交接范围使用；“在本地用于验收”与“随公开仓库发布”分开处理。
- 研究结论保留来源和证据覆盖范围；没有完整视频、逐字稿或后台数据时明确未知，不生成虚构证据。
- 会话协作授权不扩大为发布作品、发送私信、修改外部账号资料或邀请协作者的额外授权。
